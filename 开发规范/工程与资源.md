# 工程与资源（UE5）

> 目标：让"代码—资产—依赖"三者的变更都可追踪、可审查、可回滚。
> 这是 Roblox 版 `05-资源与rbxl协调.md` + `Rojo与Wally适配.md` 的对应物，但**问题形态不同**。

---

## 1. 目录结构

```
project/
├─ Source/
│  ├─ GameCore/            GameCore.Build.cs        纯 C++ 领域层
│  ├─ GameFramework/       GameFramework.Build.cs   Gameplay Framework + Subsystem
│  ├─ GameServices/        GameServices.Build.cs    存档/HTTP/资源
│  ├─ GameUI/              GameUI.Build.cs          UMG
│  ├─ GamePlay/            GamePlay.Build.cs        角色/关卡内 Actor
│  └─ ProjectName.Target.cs / Editor.Target.cs
├─ Config/                 DefaultEngine.ini / DefaultGame.ini（入库）
├─ Content/                .uasset / .umap（二进制，入库 + LFS）
├─ Plugins/                自研插件（.uplugin）
├─ docs/                   本工具链落位处（见 README）
└─ ProjectName.uproject
```

**不入库**：`Binaries/`、`Intermediate/`、`Saved/`、`DerivedDataCache/`、`*.sln`、`*.suo`、`.vs/`。

## 2. 模块依赖方向（可机检）

```
GameUI / GamePlay ──▶ GameFramework ──▶ GameCore
        │                   ▲
        └──▶ GameCore       │
GameServices ───────────────┘
```

**白名单**（脚本比对 `*.Build.cs`）：

| 模块 | 允许依赖（`PublicDependencyModuleNames`） |
|---|---|
| `GameCore` | `Core`、`CoreUObject` |
| `GameFramework` | `Core`、`CoreUObject`、`Engine`、`GameCore` |
| `GameServices` | `Core`、`CoreUObject`、`Engine`、`GameCore`、`GameFramework` |
| `GameUI` | `Core`、`CoreUObject`、`Engine`、`UMG`、`Slate`、`SlateCore`、`GameCore`、`GameFramework` |
| `GamePlay` | `Core`、`CoreUObject`、`Engine`、`GameCore`、`GameFramework` |

**禁止**：`GameCore` 依赖 `Engine` 的运行时子系统（World/Actor）；`GameCore` 被任何模块反向依赖（它在最底层）。

> 这是本工具链在 UE 上**唯一不依赖 AI 自觉**的架构约束——项目初始化第一天就建好。

## 3. 资源引用

| 规则 | 说明 |
|---|---|
| **硬引用优先（构造期确定）** | `UPROPERTY(EditDefaultsOnly) TObjectPtr<UTexture2D>` — 引用可见、被 cook 追踪 |
| **软引用（可选/大资产）** | `TSoftObjectPtr<T>` / `TSoftObjectPtr` + `StreamableManager` 异步加载 |
| **禁止写死路径** | `LoadObject<T>(nullptr, TEXT("/Game/..."))` 一律禁止（重命名后静默失败） |
| **禁止在 Tick 里加载** | 全部加载前移到初始化或异步 |
| **DataAsset 承载配置** | 不用 BP 默认值承载数值表 |

### 与 Roblox 版的根本差异

源包有一条铁律："**代码改实例名 → 必须在 Studio 同步改名**"，因为 Roblox 用字符串引用且同步工具不同步结构。**UE 里这条不成立**：资产引用是包内路径 + 导入表，重命名后 `Fix Up Redirectors` 会自动修复。

**但故障面换了个形状**，必须替换成新规则：

| 新风险 | 症状 | 防线 |
|---|---|---|
| **重定向器堆积** | 重命名后旧路径仍能加载，但资产越积越多 | 每次重命名后 **Fix Up Redirectors in Folder**，并提交删除的重定向器 |
| **写死 `/Game/` 路径** | 重定向器**只修包内引用**，修不了 C++/ini 里的字符串 | 禁写死路径（见 C3 检测）；必须用时统一走一个 `AssetPaths` 常量 |
| **`UPROPERTY` 重命名** | 序列化按属性名匹配 → **改名即丢数据** | 用 `Core Redirects`（`DefaultEngine.ini`）或加 `DeprecatedProperty` 过渡 |
| **外部移动资产** | 文件系统里移动 `.uasset` 会断引用 | **所有资产操作在 Content Browser 内做** |
| **二进制不可 merge** | `.uasset`/`.umap` 冲突无法手工解决 | 同一资产/关卡**同时只允许一人编辑**（写进团队约定） |
| **蓝图图不可 review** | 逻辑藏在 BP 里，PR 只显示 `Bin → Bin` | 见 `架构.md` §7 的 BP 边界 |

## 4. 版本控制

`.gitignore` 要点：

```
Binaries/
Intermediate/
Saved/
DerivedDataCache/
*.sln
*.suo
.vs/
```

| 规则 | 说明 |
|---|---|
| 二进制资产用 **Git LFS** | `.uasset`/`.umap`/`.png`/`.fbx`/`.wav` |
| `.uproject` / `Config/*.ini` **必须入库** | 工程配置是工程的一部分 |
| 插件：自研入 `Plugins/` 入库；市场插件评估后入 `Plugins/` 或 Fab 依赖 | 版本必须锁定 |
| 关卡/资产**独占编辑** | 写进团队约定，冲突前先沟通 |
| 提交信息含模块名 | `feat(economy): …` 便于 `git log -- <path>` 追溯 |

> **不可 merge 的资产 = 不可协作编辑**。这条不是工具问题，是流程问题，只能用"谁改谁通知"解决。

## 5. 依赖管理

| 类型 | 方式 | 注意 |
|---|---|---|
| 引擎模块 | `Build.cs` 的 `Public/PrivateDependencyModuleNames` | 只加必要项；加了就进白名单校验 |
| 自研插件 | `Plugins/<Name>/*.uplugin` | `Type: Runtime`、`LoadingPhase: Default` |
| 市场/Fab 插件 | 放 `Plugins/`，版本锁定 | 装到 **Project** 而非 Engine（否则团队环境不一致） |
| 第三方库 | `ThirdParty/` + `Build.cs` 的 `PublicAdditionalLibraries` | 记录来源与许可证 |
| Git 子模块 | `git submodule` | 锁定 commit，不用分支名 |

**【禁止】**修改 `Engine/` 目录下的任何内容（升级即丢失）；把插件装到 Engine 级；用未锁定版本的 Fab 依赖。

## 6. 配置资产纪律

| 规则 | 说明 |
|---|---|
| 配置只读 | `UDataAsset` 存策划数据，**运行时不得写回**（会污染资产） |
| 必须有校验 | 重写 `IsDataValid()`（Data Validation 插件）检查 ID 非空、范围、引用非空 |
| ID 唯一 | 命令行/编辑器脚本批量校验 DataAsset/DataTable 的 ID 冲突 |
| DataTable 用 CSV/JSON 导入 | 便于 diff 与策划编辑；**导入后提交源文件与 .uasset** |
| schema 版本 | 配置结构变更时加迁移或重新生成，不靠"默认值兜底" |
| 数值来源可溯 | 每个字段注释写明来源（策划表 / 公式 / `R{n}`） |

## 6.5 空配置与缺失资产的可加载性（三范式）

> 来源：源包 `安全隔离与空配置可加载性.md` 的实证契约。**配置为空、资产未配、字段缺失时，工程必须能启动且不报错**——否则策划一新建空表就让游戏起不来。

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| `UDataAsset` / `UTexture2D` 引用未赋值（nullptr） | 直接解引用 → 崩溃 | 加载处 **null 兜底**（默认值）+ `UE_LOG(Warning)` 一次 |
| `UDataTable` 行数为 0 / `TArray` 为空 | 假设至少一行 | 遍历 + **存在性判断**；空集合视为"功能未开启"，不报错 |
| `TSoftObjectPtr` 解析失败 | 阻塞式 `LoadSynchronous` 或断言 | **非阻塞**解析 + 失败跳过 |

**边界规则（关键）**：只有"**属性为 null / 空字符串 / 空数组**"才允许静默；一旦**填了值但填错**（格式错、ID 不存在、软引用解析失败），必须**报错**。
理由：静默会掩盖配置错误；而对"未填"报错会让空表无法启动。二者的区别是"有没有意图"。

**检测手段**：G8 `DataValidation RunAll` 只查"填了的值"的合法性，不要求"必须填"；`IsDataValid()` 里对空值返回 Valid，对填错返回 Invalid。

## 7. 构建与 CI（保守版）

| 环节 | 命令 | 频率 |
|---|---|---|
| 编译 | `Build.bat <Target> Win64 Development -Project=...` | 每次提交 |
| 编译（编辑器） | UnrealBuildTool 增量 / Live Coding | 本地 |
| 自动化测试 | `-ExecCmds="Automation RunTests <Filter>; Quit" -nullrhi -unattended` | 每次提交 |
| 模块依赖校验 | 自定义脚本比对 `*.Build.cs` | 每次提交 |
| 硬编码路径扫描 | grep `TEXT("/Game` | 每次提交 |
| RPC 权威守卫扫描 | grep Server RPC 实现体 | 合并前 |
| 打包冒烟 | `BuildCookRun -cook -stage -pak` | 合并前 / 夜间 |

**【暂不引入】**Gauntlet 多机编排、分布式构建（Incremental Build / UBA 调优）。先保证"能编译、能测、能查依赖"。

> **成本提示**：UE 冷编译 + PIE 启动是**分钟级**。CI 上必须用缓存（DDC、UBT 增量），否则门禁会因太慢被绕过——被绕过的门禁等于没有门禁。

## 8. 反模式

| 反模式 | 后果 | 正解 |
|---|---|---|
| 所有代码一个模块 | 分层失效，全量重编译 | 四模块拆分 |
| 业务逻辑写 BP | 无法 review/test/diff | 逻辑下沉 C++ |
| 在 `Content/` 外部移动资产 | 引用断裂 | Content Browser 内操作 |
| 重命名后不 Fix Up Redirectors | 重定向器堆积、加载变慢 | 每次重命名后清理 |
| 改 `UPROPERTY` 名不加 Core Redirect | 老存档/老资产丢数据 | Core Redirects 或废弃属性过渡 |
| 关卡多人同时编辑 | 二进制冲突，无法合并 | 独占编辑 |
| 插件装 Engine 级 | 团队环境不一致、升级即丢 | 装 Project 级 |
| 用 Tick 驱动一切 | 性能崩、难调试 | 计时器/事件/复制回调 |
