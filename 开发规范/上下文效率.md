# 上下文效率

> 上下文窗口是**预算**，不是无限资源。一次把整个仓库 dump 进去，换来的是"看起来读了"和"实际漏了关键文件"。
> 本文定义读取与输出的预算规则，让"信息密度"可预期。

---

## 1. 三条预算红线

| # | 红线 | 触发动作 |
|---|---|---|
| 1 | 单次命令输出预估 **> 500 tokens** | 改用过滤/限量版本 |
| 2 | 读文件**超过 200 行**且只关心局部 | 先 `grep` 定位行号，再按 `offset/limit` 读 |
| 3 | 同一次任务累计读入 **> 50 个文件** | 停下来：先画依赖图，只读核心 5–10 个 |

---

## 2. 命令映射（要什么 → 用什么）

| 需求 | 用这个 | 不要用 |
|---|---|---|
| 看改动概况 | `git status` / `git diff --stat` | `git diff` 全量 |
| 看某个函数的改动 | `git diff -U3 -- <path>` | `git diff` 全仓 |
| 找符号定义 | `grep -n "class Foo"` | 逐文件翻 |
| 找全部引用 | `grep -rn -w "Foo" src/` | 靠记忆 |
| 找最近改动 | `git log --oneline -20 -- <path>` | `git log` 全历史 |
| 列出目录 | 限 30 项 | 递归列出全部 |
| 看错误 | 编译/测试输出的**错误段** | 整个构建日志 |

> 原则：**先定位，再读全文**。定位的成本是一次 grep，读全文的成本是整个文件。

---

## 3. 排除目录（永远不要扫）

| 引擎 | 排除 |
|---|---|
| Unity | `Library/`、`Temp/`、`Obj/`、`Logs/`、`Build/` |
| UE | `Intermediate/`、`Binaries/`、`Saved/`、`DerivedDataCache/` |
| 通用 | `node_modules/`、`.git/`、第三方 vendored 目录、生成代码（`*.g.cs`、`*.generated.h`） |

在 grep 时显式排除，否则一次搜索能吞掉一半预算。

---

## 4. 什么时候**必须**要完整输出

| 场景 | 理由 |
|---|---|
| 编译/测试失败定位 | 只看最后一行会把"第一个错误"漏掉 |
| 校验工具失败（validate/门禁） | 必须看到全部失败项，否则修完一个还有三个 |
| 用户明确要求"完整输出" | 遵从 |
| 审查 diff 关键文件 | 截断的 diff 会漏掉被删的关键行 |

> 反之：**日志、构建输出、搜索结果的完整版几乎从不需要**。

---

## 5. 大文件策略

```
1. grep 关键词 → 得到行号
2. 读该行前后 30 行
3. 需要整体结构时，先读"标题/签名"（grep '^## |^class |^def '）
4. 确实要通读时，分 2–3 次读，每次读完记一句结论
```

**反模式**：一次读完 2000 行，然后凭印象回答——通常记错中间部分。

---

## 6. 卸载给子代理

| 适合卸载 | 不适合卸载 |
|---|---|
| 独立调研（"这三篇文档各讲什么"） | 需要你逐轮判断的对话 |
| 大范围扫描（"哪些文件引用了 X"） | 需要改代码的任务（除非明确隔离） |
| 只看不要结论的提取 | 与你当前上下文强耦合的推理 |

**收益**：子代理的读取不占你的上下文。
**成本**：它不理解你的隐含前提，**结论仍需你独立核对**（尤其"已完成/没问题"这类断言）。

---

## 7. 反模式清单

| 反模式 | 后果 |
|---|---|
| 把整个目录内容贴进对话 | 预算耗尽，真正关键的文件读不进来 |
| 读文件不记结论 | 读等于没读，后面还要重读 |
| 用 grep -r 全仓搜常见词（如 `id`） | 几万条命中 |
| 让 reviewer 子代理"读全部代码" | 它只会给你泛泛的意见 |
| 反复重读同一文件 | 说明没做笔记——把结论写进 `knowledge/` |

---

## 8. 效率不是省字，是省"错"

省上下文的目的不是让对话更长，而是**让关键信息有机会被读到**。

判断一个读取动作该不该做，只问一句：**这次读取能不能改变我的决定？** 不能，就别读。
