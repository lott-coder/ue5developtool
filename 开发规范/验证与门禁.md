# 验证与门禁（UE5）

> 源包（Roblox）因"无 CLI 构建链、无单元测试框架"而设计了 Phase 4.5 手动 Play 用例表。
> **UE 有 Automation / Functional Test，这条必须升级**；同时引入源包 `quality-gate.md` 的 **P0–P3 分级与数值门禁**——只有分级没有数值，门禁就是形容词。
> 本文是验收层的**唯一权威**。`verification-before-completion` 技能只补充"何时调用"，不重复本文表格。

---

## 1. 证据等级（L0–L4）

| 级别 | 证据 | 成本 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| **L0** | UBT 编译通过（0 error） | 分钟（增量秒级） | 语法/类型/反射宏/模块依赖 | 行为正确 |
| **L1** | Automation Test（`IMPLEMENT_SIMPLE_AUTOMATION_TEST`）通过，`-nullrhi -unattended` | 分钟 | 纯逻辑、数值公式、状态机、存档序列化 | World/Actor 交互 |
| **L2** | Functional Test 或带 `UWorld` 的 Automation Test | 分钟+ | Actor 交互、复制、生命周期 | 手感、视觉 |
| **L3** | PIE 手动观察 | 分钟 | 真实观感、边界情景 | 可重复性 |
| **L4** | 截图 / 录屏 / Unreal Insights | 分钟 | 视觉状态、性能数字 | 逻辑正确 |

> **UE 特有约束**：`-nullrhi` 下**渲染与 UMG 断言无效**。涉及绘制/UMG 的验证必须走 L3/L4，不能假装 L1/L2 能覆盖。

## 2. 声明 → 所需证据（强制对照表）

| 你要说的话 | 最低证据 | 不够格 |
|---|---|---|
| "编译过了" | L0（UBT 输出 0 error） | "代码看着没问题" |
| "逻辑改好了" | L1（新增/修改的 Automation 绿） | "逻辑上是这样" |
| "数值算对了" | L1（表驱动：边界/负值/溢出/NaN） | 手动点了下 |
| "存档能读写" | L1（写入→读取→迁移 三段） | "保存过一次" |
| "`UPROPERTY` 改名没丢数据" | 老存档实测载入 + 字段值正确 | "加了 Core Redirect" |
| "这个 Bug 修了" | 先复现（红）→ 修 → 同一用例转绿 | "改了这行应该好了" |
| "复制同步正常" | L2（双端）或 L3 + 日志 | "单机测过" |
| "RPC 没作弊面" | L1（非法输入被拒 + 非权威端被拦） | "加了 HasAuthority" |
| "UI 对了" | L4 截图（真实渲染，非 `-nullrhi`） | "样式写对了" |
| "性能没问题" | L4：`stat unit` / Insights 数字（见 §2.6） | "感觉挺流畅" |
| "BP 装配对了" | L3 手动 + 说明（**人工项**） | "蓝图连上了" |
| "Phase 完成" | 逐条核对产物 + 验收标准 | 单个用例过了 |
| "可以归档" | L1 全绿 + §3 门禁全部通过 | "审核说没问题" |

**铁律**：**没有新鲜证据，不许宣称完成。**

## 2.5 质量分级 P0–P3

> 来源：源包 `quality-gate.md` §0。**与审核报告的 blocking/warning/info 是两套刻度**，映射见 §2.7。

| 级别 | 含义 | 处理要求 |
|---|---|---|
| **P0（阻断）** | 破坏玩法、丢数据、可被利用作弊、崩溃、**验证自洽假象** | 未修复不得合入/发布 |
| **P1（严重）** | 明显影响体验或性能，有绕过方式 | 当前迭代内修复 |
| **P2（一般）** | 可维护性问题 | 排入任务清单 |
| **P3（建议）** | 风格与优化空间 | 鼓励，不强制 |

**P0 的典型形态**（UE 版）：
- 存档结构变更无迁移 / 载入失败静默用默认值
- `UPROPERTY` 改名/改类型无 Core Redirect（**静默丢数据**）
- Server RPC 缺 `WithValidation` 或 `HasAuthority()` 守卫
- `BlueprintReadWrite` 暴露权威状态（客户端可改）
- 业务规则写进 Blueprint（不可 diff → 不可审查）
- 测试被修改以"通过"（**验证自洽假象**）

## 2.6 数值门禁

### 2.6.1 运行时指标

| 指标 | 阈值 | 级别 | 采集方式 |
|---|---|---|---|
| 帧时间（目标设备 P95） | 按项目目标（60 FPS ⇒ ≤16.67ms）；持续 >33ms = P1 | P1 | `stat unit` / Insights |
| Game Thread / Render Thread | 任一线程超预算即 P1 | P1 | `stat unit` 分列 |
| Hitch（>100ms 卡顿） | 目标 0 次/10 分钟；出现即 P1 | P1 | Insights / 自定义埋点 |
| 峰值内存 | 按平台目标；超限触发资产瘦身评审 | P2 | `stat memory` / Insights |
| 包体增量 | > 阈值（如 100MB）需评审 | P2 | Cook 日志 |
| 崩溃率 | > 2% 触发调查 | P0 | 发布后遥测 |
| Cook 时间 | 增量 > 阈值需评审（影响迭代速度） | P2 | UAT 日志 |

**结论必须有工具数据**。`-nullrhi` 下的性能数据不可用于渲染结论。

### 2.6.2 性能基准（回归门禁）

| 规则 | 说明 |
|---|---|
| 基准必须可复跑 | 固定负载 + 固定 seed + 固定设备档 + 固定 `-nullrhi` 开关 |
| 判定三态 | `PASS`（劣化 ≤10%）/ `FAIL`（>10% 且波动 <10%）/ `NOISE`（波动 ≥10%） |
| **NOISE 不是 PASS** | 波动大的项重跑；仍不稳则该负载本身要修 |
| 取中位 | 门禁跑 3 轮取中位 |
| **基线变更需人工确认** | 禁止脚本自动覆写基线 |
| 改负载/改地图 → 旧基线作废 | 必须重收 |

UE 侧用 Automation Test + `PlatformTime`/`FPlatformTime::Seconds` 采样或 `UnrealInsights` trace，不另造框架。

### 2.6.3 安全与数据

- 权威端唯一写入口（见 `架构.md §2`）；表现层不得裁定
- Server RPC 五项校验（类型/范围/冷却/权限/距离）缺一即 **P0**
- 存档：`SchemaVersion` + 迁移 + 失败显性（见 `架构.md §5`）

## 2.7 两套刻度的映射

| 审核报告标签 | 对应 P 级 | 放行规则 |
|---|---|---|
| `blocking` | P0 / 关键 P1 | 必须修，不得归档 |
| `warning` | 一般 P1 / P2 | 可延期；单阶段 ≥5 条或跨阶段 ≥10 条 → STOP |
| `info` | P3 | 仅记录 |

## 3. 机器门禁（脱离提示词）

| # | 门禁 | 方式 | 阻断级别 |
|---|---|---|---|
| G1 | 编译 0 error | `Build.bat <Target> Win64 Development -Project="<p>.uproject"` | 阻断 |
| G2 | 无新增编译 warning | 同上，比对基线 | 警告 |
| G3 | Automation 全绿 | `UnrealEditor-Cmd.exe "<p>.uproject" -ExecCmds="Automation RunTests Project; Quit" -nullrhi -unattended -ReportExportPath=<dir>` | 阻断 |
| G4 | 模块依赖白名单 | 脚本比对 `*.Build.cs` | 阻断 |
| G5 | 硬编码 `/Game/` 路径 | grep `TEXT("/Game` | 阻断 |
| G6 | 关键路径 Functional Test | `-ExecCmds="Automation RunTests Project.Functional; Quit" -nullrhi` | 阻断（合并前） |
| G7 | Server RPC 权威守卫 | grep RPC 实现体是否含 `HasAuthority()` | 阻断（合并前） |
| G8 | Data Validation | `-ExecCmds="DataValidation RunAll"` | 警告 |
| G9 | 重定向器残留 | 脚本检查 `Content/` 下 redirector 数量 | 警告 |

> **落地顺序**：G1 → G3 → G4 → G5（一天可完成），其余随后。

## 4. 测试分层

| 层 | 测什么 | 用什么 | 占比 | 相对成本 |
|---|---|---|---|---|
| `GameCore` | 公式、状态机、边界 | `IMPLEMENT_SIMPLE_AUTOMATION_TEST`（**无 World**） | 70% | 最低 |
| `GameFramework` | 子系统编排、复制、RPC 校验 | `IMPLEMENT_COMPLEX_AUTOMATION_TEST` 或 Functional Test | 25% | 中 |
| `GameServices` | 存档序列化、迁移 | Automation Test（`USaveGame` 纯数据） | 含上 | 低 |
| `GameUI` / `GamePlay` | 关键交互链路 | Functional Test + 手动 L3/L4 | 5% | 最高 |

**为什么以纯 C++ 测试为主**：World 测试需要启动引擎、加载地图、跑 tick，单条成本是纯逻辑测试的几十倍，CI 上容易超时。把逻辑挤到 `GameCore` 是唯一可持续的策略。

### Automation Test 骨架

```cpp
#include "Misc/AutomationTest.h"

IMPLEMENT_SIMPLE_AUTOMATION_TEST(FEconomyPriceTest, "Project.Economy.PriceRule",
    EAutomationTestFlags::EditorContext | EAutomationTestFlags::EngineFilter)

bool FEconomyPriceTest::RunTest(const FString& Parameters)
{
    TestEqual(TEXT("base price"), ComputePrice(100, 1.0f), 100);
    TestEqual(TEXT("NaN guard"), ComputePrice(100, NAN), 100);
    return true;
}
```

## 5. 验收标准怎么写（Phase 1/3 强制格式）

| # | 验收项 | 证据级别 | 具体判据 |
|---|---|---|---|
| AC-1 | 余额足够时购买成功 | L1 | `TryBuy` 返回 true；`TotalCoins` 减少 price；库存 +1 |
| AC-2 | 余额不足整体拒绝 | L1 | 返回 false + `INSUFFICIENT`；两值**均不变** |
| AC-3 | 重复请求幂等 | L1 | 同 `RequestId` 两次，只发货一次 |
| AC-4 | 脏输入不崩 | L1 | NaN / 负数 / 超大值 → 拒绝且状态不变 |
| AC-5 | 服务端权威 | L1 | 非权威端调用被 `HasAuthority()` 拦截 |
| AC-6 | 按钮置灰与提示 | L4 | 截图：余额不足时按钮灰、显示差额 |

## 6. 手动验证（保留，但明确边界）

| 场景 | 为何不能自动 |
|---|---|
| 手感、镜头、打击感、动画过渡 | 主观体验 |
| UMG 布局/多分辨率/多语言 | 需真实渲染（`-nullrhi` 无效） |
| 长时间运行泄漏 | 需长跑 |
| 平台相关（主机/手柄） | 需真机 |
| **Blueprint 装配正确性** | 图不可断言（人工项 M2） |

**要求**：手测必须留 **L4 证据 + 一句"我看到了什么"**，写进 `05-issues.md`。

---

## 7. 调试纪律

| 阶段 | 动作 |
|---|---|
| 1. 复现 | 写一个**能稳定变红**的 Automation Test |
| 2. 定位 | `UE_LOG` + 分类过滤 / 断点 / Insights / 二分；**先证伪假设** |
| 3. 修复 | 改最小面；补防回归测试 |
| 4. 验证 | 红→绿；跑相邻用例；涉及联机则双端验证 |

---

## 8. 反模式

| 反模式 | 后果 |
|---|---|
| 用"逻辑上应该对"替代测试 | 未验证的东西被固化成 `spec/` 真相 |
| 所有测试都做成 World 测试 | CI 超时，最终没人跑 |
| 依赖 PIE 手测为主 | 不可重复，回归靠运气 |
| 在 `-nullrhi` 下断言渲染 | 假绿（永远不触发真实绘制） |
| 改测试预期来通过 | 门禁失效（**P0**） |
| 只写"性能 OK"不给数字 | 无法判断劣化 |

## 9. UI 验收（清单式双闸门）

> 迁移自源包 `roblox-ui-design` 的"构建者机检 + 独立审查员"双闸门**思想**（其 17 项审计是 Roblox GUI 专属，不可照搬）。
> UE 的 UI 是 UMG/Slate，门禁改为**同一份清单、两个角色**：

| 角色 | 做什么 | 不能做什么 |
|---|---|---|
| **构建者** | 交付前**逐条自查**并写进 `05-issues.md` | 不能给自己判"通过" |
| **独立审查员**（不参与构建） | 用**同一份清单**复核，重点看构建者**没提到**的项 | 不能边审边改（只报告） |

**清单（每条给证据）**：

| # | 检查 | 证据 |
|---|---|---|
| U1 | 布局：目标分辨率与常见 16:9 / 21:9 下不错位、不溢出 | 截图 ×2 以上 |
| U2 | DPI / 安全区：DPI Curve 正确、刘海/电视过扫描不遮挡 | 截图或配置 |
| U3 | 四态齐全：空 / 加载 / 正常 / 错误（含禁用态） | 截图或状态表 |
| U4 | 异步等待有**超时**与失败提示（禁止无限转圈） | 代码位置 + 截图 |
| U5 | 可点区域与焦点可达（手柄/键盘可导航，焦点顺序合理） | 操作步骤 |
| U6 | 点击有即时反馈（<100ms），长操作有 loading | 录屏 |
| U7 | 文案走 `FText` + 本地化表，无硬编码 | grep 证据 |
| U8 | ZOrder/层级正确（弹窗盖住背景、不吞点击） | 截图 |
| U9 | 无每帧 `Invalidate`/重建 Slate 的坏习惯；Widget 只在数据变化时刷新 | Insights 或代码 |
| U10 | 退出/关闭路径明确（ESC、返回键、手柄 B） | 操作步骤 |

**放行规则**：U1–U4 任一未过 = 阻断（P1）；其余未过 = 记录后可交付。
**审查员交付物**：`04-review-report.md` 追加「UI 审查」一节。

> 现状：**没有自动化结构审计脚本**。本清单是人工/截图级门禁，不要假装成机检。
