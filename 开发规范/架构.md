# 架构（UE5 · 保守版 v0.1）

> **本文的边界**：只写"已确认能在 UE 5.4+ 上落地"的做法——每项都基于**引擎原生能力**，不依赖插件市场、不依赖第三方框架、不依赖自定义构建工具。
> 标注 **【暂不采用】** 的条目是**刻意排除**：它们要么把边界变成运行时协商（无法静态审查），要么把迭代回路拉长到流程无法承受。
> 改本文 = 改所有后续迭代的前提，需走 `/workflow`。

---

## 1. 分层：四个模块 + 引擎原生 Gameplay Framework

Knit 的 Service / Controller / Shared 在 UE 里**不能 1:1 照搬**——UE 已经有一套强制的 Gameplay Framework（GameMode / GameState / PlayerController / PlayerState / Pawn），再造一层 "Service" 会得到**两套权威模型**。

**正确做法**：把 Knit 的"职责划分"映射到 UE 已有的承载物上，而不是新建平行层。

| 层 | 模块（`.Build.cs`） | 承载物 | 职责 | 允许依赖 |
|---|---|---|---|---|
| **Domain** | `GameCore` | 纯 C++ 结构/算法（`USTRUCT`、无 `UWorld` 访问） | 数值公式、规则、状态机 | 仅 `Core`（不依赖 `Engine` 的运行时服务） |
| **Gameplay** | `GameFramework` | `AGameMode` / `AGameState` / `APlayerController` / `APlayerState` / `UGameInstanceSubsystem` / `UWorldSubsystem` | 会话编排、**唯一写入口**、权威判定 | `GameCore` |
| **Infrastructure** | `GameServices` | `USaveGame`、HTTP、`UAssetManager`、平台接口 | 存档、网络传输、资源加载 | `GameCore`、`GameFramework` |
| **Presentation** | `GameUI` / `GamePlay` | UMG `UUserWidget`、`UAnimInstance`、Niagara、`ALevelScriptActor` | 表现、输入响应、VFX | `GameCore`、`GameFramework`（只读） |

### 映射对照（便于理解，不要照抄命名）

| 源包（Roblox/Knit） | 本文（UE5） |
|---|---|
| Service（服务端权威） | **Gameplay** 层：GameMode/GameState（对局）+ Subsystem（无对局归属的服务） |
| Controller（仅表现） | **Presentation**：`APlayerController`（输入/视角）+ UMG |
| Shared Config（纯数据表） | **`UDataAsset` / `UDataTable` / GameplayTags** |
| Knit 单例 | 拆成三种生命周期：GameInstance（跨关卡）/ World（关卡内）/ Actor（实体） |

> **反模式警告**：不要造 `UServiceBase` + `UServiceManager` 再去管理 GameMode。那会和引擎的框架打架，出现"两个地方都能改对局状态"。

### 为什么用模块边界而不是"靠自觉"

`Build.cs` 的 `PublicDependencyModuleNames` / `PrivateDependencyModuleNames` 是**编译期硬约束**：`GameCore` 不声明依赖 `GameUI`，就永远不可能反向引用。

**检测手段**：脚本比对每个 `*.Build.cs` 的依赖白名单（见 [工程与资源.md](工程与资源.md) §2）。

## 2. 权威模型：用引擎原生 `HasAuthority()`，只做二选一

UE 的权威模型比 Unity **更接近 Roblox**：默认服务器权威，`HasAuthority()` 是引擎级事实，不是需要自己发明的约定。

| 模式 | 适用 | 权威位置 | 写入口 |
|---|---|---|---|
| **A. Standalone（单机）** | 单机、离线、原型 | 进程内即权威（`HasAuthority()` 恒为 `true`） | Gameplay 层唯一写入口 |
| **B. Dedicated Server（联机）** | 联机对战、含交易 | 服务器进程 | Gameplay 层唯一写入口（仅服务器执行） |

**关键利好**：A 与 B 用**同一套代码**——`if (!HasAuthority()) return;` 在单机下永不拦截，联机下拦截非权威端。这意味着"单机先做，后面加联机"不需要重写业务层。

**【暂不采用】**

| 项 | 为何排除 |
|---|---|
| **Listen Server（Host 即玩家）** | Host 玩家拥有权威 → "host 可见状态"无法防作弊。若产品必须支持，需在架构文档**显式声明**并接受该限制，且不得声称有反作弊保证 |
| **Client-side prediction / rollback** | 需要确定性模拟与网络建模，属于有明确需求后再做 |
| **Replication Graph / Iris** | 大规模同步优化，与"可审查的最小架构"目标相反 |

> **保守版的代价与收益**：放弃 Listen Server 会牺牲"一键联机"的便利；收益是**权威边界重新变成可静态审查的事实**——`HasAuthority()` 一出现就能判断这段逻辑属于哪一端。

**检测手段**：所有 Server RPC 实现体内必须出现 `HasAuthority()` 守卫；脚本/grep 可在 PR 时校验（见 [验证与门禁.md](验证与门禁.md) §3）。

## 3. 通信：RPC 只做薄入口，复制承载状态

| 通道 | 机制 | 用途 | 约束 |
|---|---|---|---|
| **进程内** | C++ 委托（`DECLARE_DYNAMIC_MULTICAST_DELEGATE`）/ 直接调用 | ~85% | 默认选它 |
| **状态同步** | `UPROPERTY(Replicated)` + `GetLifetimeReplicatedProps` | 客户端需要"看到"的状态 | 只复制必要字段；不进复制的留在服务器 |
| **请求/响应** | `UFUNCTION(Server, Reliable)` | 客户端发**意图** | 必须 `HasAuthority()` 守卫 + 五项校验 |
| **广播** | `UFUNCTION(Client/Multicast, Reliable)` | 表现事件 | 不得携带权威状态变更 |

### RPC 的唯一正确形状

```cpp
// 客户端：只表达意图
void AMyPlayerController::RequestBuy(const FString& ItemId)
{
    ServerRequestBuy(ItemId);
}

// 服务端：解包 → 校验 → 转发给 Gameplay 层
bool AMyPlayerController::ServerRequestBuy_Validate(const FString& ItemId) { return !ItemId.IsEmpty(); }

void AMyPlayerController::ServerRequestBuy_Implementation(const FString& ItemId)
{
    if (!HasAuthority()) return;
    // 五项校验：类型/范围/冷却/权限/距离
    if (!IsValidItemId(ItemId)) return;
    GetGameInstance()->GetSubsystem<UEconomySubsystem>()->TryBuy(GetPlayerState(), ItemId);
}
```

❌ 错误：RPC 里写结算逻辑（无法单测、无法复用、客户端与服务端逻辑分叉）
✅ 正确：RPC 只做"解包 + 校验 + 转发"，结算在 Gameplay 层，结果通过**复制属性**回传

**命名约定**：Server RPC 用 `Server` 前缀；Client RPC 用 `Client` 前缀；Multicast 用 `Multicast` 前缀——引擎的反射宏会按前缀做校验，**命名错会静默不复制**（这是 UE 最常见的联机坑之一）。

## 4. 生命周期：三段式（替代 BeforeLoad/AfterLoad）

Roblox 版用 `player:GetAttribute("Loaded")` 做关卡。UE 的对应问题是**三个层级的初始化顺序**：

```
① GameInstance 级（跨关卡，进程内唯一）
   UGameInstanceSubsystem::Initialize()
   └─ 加载配置（DataAsset）、建立会话、注册全局服务

② World 级（关卡加载后）
   UWorldSubsystem::OnWorldBeginPlay() / AGameMode::BeginPlay()
   └─ 生成玩家、初始化对局、读取存档 → 置 bWorldReady

③ 表现级（数据就绪后）
   UUserWidget::NativeConstruct() 时订阅委托
   └─ 只读状态、只发表演，不得假设①已就绪（除非显式检查）
```

**硬规则**：
- 表现层**不得**在 `NativeConstruct` 里直接读取可能未就绪的数据 → 必须订阅就绪委托或用 `UWorldSubsystem` 的 `IsReady()`
- 跨关卡状态放 GameInstance 级；**不要**放 GameMode（关卡切换即销毁）
- 等待必须有超时或显式失败，禁止无限 `GetWorld()->GetTimerManager().SetTimer` 轮询
- `GameMode` 只在服务器存在；客户端**永远拿不到** `GameMode`（这是引擎设计，不是约定）

**检测手段**：`A*GameMode` 内出现 `IsLocallyControlled()` / `GetNetMode() == NM_Client` 分支即为可疑（GameMode 本就不该在客户端运行）。

## 5. 数据：单机用 `USaveGame`，联机必须走后端（不可混用）

Roblox 版的核心教训是"**部分更新会静默丢字段**"（客户端浅替换）。这条在 UE 里同样成立。

| 场景 | 存储 | 规则 |
|---|---|---|
| **单机** | `USaveGame` + `UGameplayStatics::SaveGameToSlot` | 本地文件，**玩家可篡改** → 只用于单机/离线 |
| **联机** | 后端（自建 / PlayFab / EOS） | 权威数据只在服务器；**禁止**用 `USaveGame` 存权威数据 |

**通用规则（两种场景都适用）**：

| 规则 | 说明 |
|---|---|
| **整块快照** | 更新某分区时序列化**整个分区**，读取侧整分区替换，不做字段级合并 |
| **schema 版本** | `USaveGame` 子类/后端记录必须有 `SchemaVersion`；按版本迁移 |
| **原子写** | 先写临时槽位 → 校验 → 替换；保留上一版 |
| **失败即显性** | 载入失败必须报错并阻断进入，**禁止静默用默认值开局**（等于覆盖存档） |
| **幂等标记** | 一次性奖励/首登发放必须有 `bGranted` 或计数 |

**【暂不采用】**云存档/后端接入（首版）——直到出现跨设备或联机结算需求。
**边界声明**：一旦需要联机持久化，`USaveGame` **不能**充当权威存档，必须换后端——这条要在架构文档提前写明，避免后期返工。

**检测手段**：`USaveGame` 字段变更需同步 `SchemaVersion`；`Automation Test` 覆盖"旧版本→新版本"往返。

## 6. 模块划分：按业务域，不按技术层

✅ 按业务域：`Inventory`（获得/消耗/上限）、`Shop`（购买/发货/退款）、`Progression`（经验/等级/解锁）
❌ 按技术层：`SaveManager`、`NetworkManager`（这些是 Infrastructure 的工具，不是业务模块）

| 判断 | 结论 |
|---|---|
| 能用一句话讲清"负责游戏的哪一块" | 是业务模块 |
| 只能讲清"它是个工具" | 是 Infrastructure 或 Utility |
| 两个模块频繁互调 | 边界划错，合并或重切 |
| 单文件 > ~500 行且有多个独立子主题 | 拆成子目录 + 子模块 |
| 起步就建 20 个空模块 | 过度设计，先 3–5 个 |

**模块分类表（`change/` 与 `knowledge/` 的目录名，需按项目重定义）**：

| 模块 | 范围 |
|---|---|
| `core` | 启动、生命周期、领域基础类型 |
| `data` | 存档、schema 迁移、配置加载 |
| `economy` | 货币、价格、结算、账本 |
| `progression` | 经验、等级、解锁 |
| `ui` | UMG、HUD、弹窗 |
| `audio` | BGM/SFX（MetaSounds/音频组件） |
| `_misc` | 无法归类的 |

## 7. Blueprint 边界（本规范最重要的一条）

**BP 无法 diff、无法被文本审查、无法被 agent 可靠读写。** 因此：

| 允许放 BP | 禁止放 BP |
|---|---|
| 装配（挂 C++ 组件、继承 C++ 基类/接口） | 业务规则、数值公式 |
| 绑事件、设默认值、配 DataAsset 引用 | 结算、扣费、发奖 |
| 纯表现（特效时序、音效触发） | 存档写入、权威判定 |
| 关卡蓝图里的场景编排 | 任何"必须这样"的契约行为 |

**判据**：这段逻辑**是否需要被测试、被审查、被 spec 记录**？需要 → C++。

**检测手段**（诚实分级）：
- 可自动：C++ 侧静态检查、AssetRegistry 查 BP 是否实现了禁用接口
- **只能人工**：BP 图内部的逻辑复杂度 → 靠 PR 清单 + 评审
- 因此：**BP 默认不进入 `code-reviewer` 的自动检查范围**，只在 `knowledge/` 记录"哪个 BP 负责什么装配"

> 这条是迁移到 UE 时最大的语义损失：**文档可治理的覆盖面从"全部代码"收缩到"C++ + 数据层"**。承认它，比假装 BP 也能治理要好。

## 8. 可验证性声明：每条约束必须有检测手段

**写进文档但无法检测的约束，一律降级为建议。**

| # | 约束 | 检测手段 | 级别 |
|---|---|---|---|
| C1 | 模块依赖方向 | `*.Build.cs` 依赖白名单脚本比对 | 阻断 |
| C2 | Server RPC 有 `HasAuthority()` 守卫 | grep RPC 实现体 | 阻断 |
| C3 | 禁写死 `/Game/...` 路径字符串 | grep `TEXT("/Game` | 阻断 |
| C4 | 禁运行时 `LoadObject` 同步加载 | grep `LoadObject<` / `StaticLoadObject` | 警告 |
| C5 | 复制属性声明完整 | 脚本检查 `Replicated` 字段是否出现在 `GetLifetimeReplicatedProps` | 警告 |
| C6 | `UPROPERTY` 重命名不丢数据 | ❌ 无法自动检测 → **人工清单** | 人工 |
| C7 | BP 不含业务逻辑 | ❌ 无法自动检测 → **人工评审** | 人工 |
| C8 | 关键行为有 Automation Test | 测试命名/目录存在性 | 警告 |

> **C6/C7 标"人工"是有意为之**：UE 里这两条确实无法可靠自动化。把它们标成"可检测"才是真正的风险。

## 9. 保守边界总表（迁移决策留痕）

| 项 | 采用 | 暂不采用 | 理由 |
|---|---|---|---|
| 分层 | 四模块 + 原生 Gameplay Framework | 自造 Service 层 | 避免双权威源 |
| 权威 | Standalone / Dedicated | Listen Server、预测回滚、Replication Graph/Iris | 权威边界须可静态确认 |
| 通信 | 原生 RPC + Replicated 属性 | 第三方网络层、自建消息总线 | 减少状态搜索空间 |
| 数据 | `USaveGame`（单机）/ 后端（联机，二期） | 云存档首版接入 | 无并发写入者前是纯成本 |
| 能力系统 | Gameplay Framework + C++ 模块 | **GAS（首版）** | GAS 是完整范式，先让流程跑起来；有技能/buff 复杂度需求时再引入 |
| 配置 | `UDataAsset` / `UDataTable` / GameplayTags | 运行时热更 | 先要编译期/编辑期校验 |
| 自动化 | Automation Spec + Functional Test | Gauntlet 多机编排 | 成本过高，需求出现再说 |
| 可视化脚本 | BP 只做装配 | BP 承载业务逻辑 | 不可 diff → 不可审查 |
| 构建 | UBT 增量 + Live Coding | 自研构建管线 | 引擎原生已足够 |

> **每一项都可单独升级，且升级不改变流程**——这是保守版的真正价值：**先让流程跑起来，再让架构长大**。

## 10. 与 Unity 版的关键差异（同一方法论的两种宿主）

| 维度 | Unity 版 | UE5 版 |
|---|---|---|
| 权威 | 需**自建**（默认允许 client-host） | **原生**（`HasAuthority()`，Standalone 下恒 true） |
| 分层强制 | `asmdef` 引用 | `Build.cs` 依赖 |
| 可视化脚本 | 不涉及 | **必须划边界**（BP 不可审查） |
| 迭代延迟 | 秒–分钟 | **分钟**（编译 + PIE）→ 自治模式受限 |
| 测试 | Test Framework（EditMode 优先） | Automation Spec / Functional Test |

> 结论：**UE5 在"权威建模"上更容易，在"文档可治理性"上更难。** 方法论必须在后者上做让步。
