# 技能与代理使用

> 本工具链有 3 类可调用单元：**skill**（流程/纪律）、**agent**（隔离评审）、**command**（薄包装）。
> 用错类型比不用更糟：把纪律当流程走会僵化，把评审当自审会漏判。

---

## 1. 三类单元的定位

| 类型 | 是什么 | 典型 | 是否消耗主上下文 |
|---|---|---|---|
| **skill** | 一段可复用的**流程或纪律**，在同一上下文内执行 | `workflow`、`brainstorm-*`、`knowledge-*`、`verification-*`、`systematic-debugging` | 是 |
| **agent** | 独立上下文的**评审者/提取者**，只看你给的材料 | `plan-reviewer`、`code-reviewer`、`prd-reader` | 否（结果才回来） |
| **command** | 斜杠命令，是 skill 的薄包装 | `/workflow`、`/brainstorm-design` | 是（转发给 skill） |

---

## 2. 什么时候用哪个

| 你的处境 | 用 | 不要用 |
|---|---|---|
| 需求模糊，不知从哪下手 | `brainstorm-design` | 直接写代码 |
| 需求清楚，但要定技术方案 | `brainstorm-develop` | 边写边想 |
| 要跑完整迭代（需求→计划） | `workflow plan` | 手动逐篇写文档 |
| 文档写完了，要独立审一遍 | `plan-reviewer`（agent） | 自己再读一遍（会看不见自己的盲点） |
| 代码写完了，要按规范查 | `code-reviewer`（agent） | 让写代码的人自审后直接提交 |
| 读 PRD 截图/PDF 转需求 | `prd-reader`（agent） | 自己边看图边猜 |
| 要改某模块但不懂现状 | `knowledge-get` | 直接读代码猜设计意图 |
| 踩了个坑想记下来 | `knowledge-set` | 写进代码注释（会丢） |
| 需求定了，但要判断"值不值得做/留不留得住人" | `experience-designer`（agent） | 自己拍脑袋 |
| 要定技术方案、判分层与可测性 | `{engine}-systems-engineer`（agent） | 边写边想 |
| 准备说"完成了" | `verification-before-completion` | 凭印象宣布 |
| Bug 难复现 | `systematic-debugging` | 改代码试 |
| 要批量删/改名 | `代码清理.md` 的纪律 | 全仓正则一把梭 |

---

## 3. agent 的调用纪律

### 必须调用的时机（不可省）

| 阶段 | agent | 产物 |
|---|---|---|
| Phase 0 | `prd-reader` | `00-prd-analysis.md` |
| Phase 1 后 | `plan-reviewer`(requirements) | 追加 `04-review-report.md` |
| Phase 1（并行） | `experience-designer` | 体验/留存/变现意见（不阻断） |
| Phase 2 前（可选） | `{engine}-systems-engineer` | 分层落位与可测性评估 |
| Phase 2 后 | `plan-reviewer`(design) | 追加 |
| Phase 3 后 | `plan-reviewer`(plan) | 追加 |
| Phase 4 后 | `code-reviewer` | 追加 |

### 调用时该给什么

| 给 | 不给 |
|---|---|
| 明确的**审核类型** | "帮我看看" |
| **文档/文件路径**（让它自己读） | 把全文粘进 prompt |
| **规范路径**（`开发规范/*.md`） | 让它猜规范 |
| 原始需求摘要（一句话） | 你的实现思路（会带偏） |

### 采信纪律

- agent 说"通过"→ **你仍要自己看 diff**（它的上下文里没有你的隐含前提）
- agent 说"有问题"→ **逐条核对**，不因为"它是独立评审"就照单全收
- agent 的结论**必须落盘**（`04-review-report.md`），口头结论不算
- **规范是否真读完，看末行标记**：每篇 `开发规范/*.md` 末尾都有 `<!-- 已读到文末: <名> -->`。
  若 agent 声称"符合规范"却报不出该标记，说明它只 grep 了片段——**其结论按"未读"处理**，要求它重读或由你亲自核对。
  这条替代原版"回复开头附古诗"的做法：可机检、不污染交付物。

## 4. 反模式

| 反模式 | 后果 |
|---|---|
| 让 `code-reviewer` "读整个仓库" | 它只会给泛泛建议，且极慢 |
| 自己审完就跳过 agent | 单一视角，盲点必现 |
| 同一步骤重复调 3 次 agent | 浪费时间且不会更准；改为先修明显问题 |
| 把 agent 的"没问题"当成验证证据 | 它没跑测试，只读了代码 |
| 用 `--unattended` 跑需求探索阶段 | 需求需要一起想，不是自动决策的对象 |
| 跳过 `knowledge-get` 直接改 | 重复踩已知的坑 |

---

## 5. 写一个新 skill 的判断标准

不是所有"有用的做法"都值得做成 skill。满足以下**全部**才做：

1. 会被**反复使用**（≥3 次/项目）
2. 有**明确步骤**（能写成清单，而不是"要有经验"）
3. 有**可判定的产出**（文档/文件/结论）
4. 能与现有 skill **划清边界**（否则会互相抢触发）

否则：写进 `knowledge/{module}.md` 或 `开发规范/` 即可。

---

## 6. 成本意识

| 单元 | 相对成本 | 何时值得 |
|---|---|---|
| skill 全过程 | 中–高（多轮交互） | 需求/方案确实需要澄清 |
| `--direct` 模式 | 低 | 需求已明确的小改动 |
| agent 评审 | 中（独立上下文） | 每个阶段至少一次，**不可省** |
| `--unattended` | 高（含返工） | 需求明确且改动局限在可测层 |

> 判断标准：**这个调用能否降低"返工一次"的概率？** 能，就值得；不能，就是流程表演。
