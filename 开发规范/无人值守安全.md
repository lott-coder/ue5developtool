# 无人值守安全（`--unattended`）

> 本文是 `--unattended` 的**唯一权威**：严重度矩阵只在这里定义，其它文档引用它。
> **UE 的特殊约束**：编译分钟级、资产二进制、Blueprint 不可审查——爆炸半径比 Unity 更大。

版本：v2.0.0｜适用：`/workflow plan --unattended [--cron]`

---

## 1. 核心差异（与交互模式）

| 交互模式 | `--unattended` |
|---|---|
| Phase 1/2 的 brainstorm 问答 | 跳过，降级为 `--direct` |
| 方案选择（精简/标准/旗舰） | 自动选「标准」 |
| 审核后 `AskUserQuestion` | 严重度矩阵自动决策（§2） |
| 用户确认进入下一阶段 | 自动（0 阻断 且 警告 < 5） |
| 修复决策 | 自修复循环（非安全类最多 2 轮） |
| 手动验证（L3/L4） | 一律标记 `unverified` |
| 归档 | **不自动归档**，只生成就绪报告 |

---

## 2. 严重度自动决策矩阵（唯一权威定义）

```
审核完成 → 解析严重度
  ├─ 含「安全阻断」？        → HARD STOP ✋（不进入自修复）
  ├─ 含普通阻断？            → 自修复 ≤2 轮 → 仍未过 → STOP
  ├─ 0 阻断 + 警告 ≥ 5 条？  → STOP（质量滑坡防护）
  ├─ 0 阻断 + 警告 < 5 条？  → 自动放行 ✓
  └─ 0 阻断 + 0 警告？       → 静默放行
```

跨阶段累计警告 ≥ 10 → 全局 STOP。

> `工作流执行.md` 不再重复本矩阵，只引用本节。

---

## 3. 安全阻断清单（出现即 HARD STOP，禁止自动修复）

| # | 类型 | 为何不可自动修 |
|---|---|---|
| 1 | 改权威模式（Standalone ↔ Dedicated，或引入 Listen Server） | 影响全部现有代码与验收标准 |
| 2 | 引入/升级插件或第三方库（`.uplugin`、`Build.cs` 依赖） | 团队环境与打包行为变更 |
| 3 | 修改模块依赖白名单（`*.Build.cs`） | 分层是唯一硬约束 |
| 4 | 修改存档 `SchemaVersion` 且无迁移 | 玩家存档不可读（不可逆） |
| 5 | **重命名/删除 `UPROPERTY` 且无 Core Redirect** | 序列化按名匹配 → 静默丢数据 |
| 6 | 存档载入失败时静默用默认值 | 等于覆盖玩家存档 |
| 7 | 删除或移动任何资产（`.uasset`/`.umap`） | 引用断裂、重定向器堆积 |
| 8 | 修改 `Config/Default*.ini` | 工程级行为变更（含 Core Redirects） |
| 9 | **修改 Blueprint 的业务逻辑** | 不可 diff → 不可审查（违反 BP 边界） |
| 10 | 在 `Tick` 内新增查找/分配/同步加载 | 性能回归且难定位 |
| 11 | Server RPC 无 `HasAuthority()` 守卫 | 权威边界失守 |
| 12 | 写死 `/Game/...` 路径 | 重命名后静默失败 |
| 13 | **修改测试以通过门禁** | 门禁失效（P0） |
| 14 | `try/catch` 吞异常 / 空 catch | 掩盖故障 |

> 判定规则：**只要"改错的后果不可逆或不可检测"，就是安全阻断。**

---

## 4. 运行约束（HARD STOP 条件）

| 约束 | 阈值 | 说明 |
|---|---|---|
| 单次自动生成文件数 | ≤ 10 | 不含 `05-issues.md` 与进度文件 |
| 单 Phase 耗时 | **≤ 45 分钟** | 比 Unity 放宽：UE 冷编译本身 10–20 分钟 |
| 单发现自修复轮次 | ≤ 2 | 超限 STOP |
| 单 Phase 总修复轮次 | ≤ 3 | 超限 STOP |
| WIP 无推进时长 | ≤ 24 小时 | 标记 `stale` + STOP |
| 并发执行 | 一个 `change/{module}/_tmp/` 只允许一个进程 | 取锁失败即退出 |
| **连续编译失败** | ≤ 3 次 | 第 3 次仍失败 → STOP（防死循环烧时间） |

---

## 5. 绝对禁止

- ❌ `git commit` / `git push`
- ❌ 修改 `.uasset` / `.umap` / `Config/*.ini`
- ❌ 修改 `Plugins/` 与 `*.uplugin`
- ❌ 执行 `BuildCookRun` / 打包 / 部署
- ❌ 删除任何文件
- ❌ 跳过 `plan-reviewer` / `code-reviewer`

**允许**：读写 `Source/**/*.h|*.cpp`、`Source/**/Tests/**`、`docs/**`、`change/`、`spec/`、`knowledge/`。

---

## 6. Phase 判定（按 `_tmp` 文档存在性）

| 条件 | 当前 Phase |
|---|---|
| `00-prd-analysis.md` 存在但 `01-requirements.md` 不存在 | Phase 1 |
| `01` 存在但 `02-design.md` 不存在 | Phase 2 |
| `02` 存在但 `03-plan.md` 不存在 | Phase 3 |
| `03` 存在但未标记「全部完成」 | Phase 4 |
| `03` 全部完成 + code-review 已通过 | Phase 5 |
| `.unattended-progress.json` 有 `stoppedReason` | **SKIP** |
| `_tmp/` 为空 | **SKIP** |

**模块处理顺序**：字母序；多模块串行。

---

## 7. 边界处理

| 场景 | 处理 |
|---|---|
| `_tmp/` 为空 | SKIP |
| 并发 Cron 触发 | `change/.unattended.lock`（<30min 拒绝，≥30min 接管） |
| 会话崩溃 | 锁过期后重入，从进度文件恢复 |
| WIP >24h 无推进 | `stoppedReason="stale-timeout"` |
| 审核结果为空 | 视为通过 |
| Agent 报错 | 重试 1 次 → 仍失败 → STOP |
| 编译失败 | 计数 +1，≤3 次 |
| 已存在 `stoppedReason` | SKIP |

---

## 8. UE 自治模式的适用边界（关键）

| 任务类型 | 是否适合自治 | 原因 |
|---|---|---|
| `GameCore` 纯逻辑 | ✅ **适合** | 可 L1 测试、增量编译快、无资产 |
| `GameFramework` 子系统 | ⚠️ 谨慎 | 需 World 测试，验证成本高 |
| `GameServices` 存档 | ⚠️ 谨慎 | 涉及迁移，安全阻断高频区 |
| `GameUI` / UMG | ❌ 不适合 | 验证需人眼（`-nullrhi` 无效） |
| Blueprint 装配 | ❌ 不适合 | 不可写、不可审查 |
| 涉及复制/网络 | ❌ 不适合 | 需双端验证 |

> **默认只对 `GameCore` 开放**。其余模块走交互模式。

---

## 8.1 可自动修复的范围（正面清单）

**可以修**：文档文本修正、补 `UPROPERTY()` 缺失声明、补 `HasAuthority()` 守卫、补输入校验桩、补超时/计时器清理、修正常量命名、补 `EndPlay` 解绑。

**不可以修**：存档 schema 与迁移、权威层职权重划、资产增删改名、依赖与工程配置、Blueprint 逻辑、任何需人眼判断的视觉问题。

## 9. 进度跟踪

```json
{
  "mode": "unattended",
  "startedAt": "2026-11-12T10:30:00Z",
  "currentPhase": "phase3",
  "scope": "GameCore only",
  "phases": {
    "phase1": {"status": "auto-passed", "completedAt": "…", "blockingFindings": 0, "warnings": 1}
  },
  "repairRounds": {"requirements": 0, "design": 0, "plan": 0, "code": 0},
  "buildFailures": 0,
  "autoGeneratedFiles": 3,
  "stoppedReason": null
}
```

`stoppedReason` 枚举：`security-blocking` / `self-repair-failed` / `quality-guard` / `stale-timeout` / `agent-error` / `build-failed` / `null`

---

## 10. 恢复流程

1. 读 `05-issues.md` → 2. 读进度文件 → 3. 人工修复 → 4. 清空 `stoppedReason`、重置 `buildFailures` → 5. 重跑或手工完成。

---

## 11. 完成报告（强制）

写入 `05-issues.md` 的「无人值守执行完成报告」章节，含每 Phase 状态/阻断/警告/待人工事项（模板见 `模板/05-issues.md` §5）。

---

## 12. `--cron` 轮询模式

| 项 | 定义 |
|---|---|
| 行为 | 每 N 分钟读 `versions.json`，对 `status=wip` 模块按字母序处理 |
| 无 WIP | 等待下一周期 |
| 有 WIP 但已 STOP | SKIP（不覆盖 `stoppedReason`） |
| 退出 | 用户中断 / 文件上限 / 连续 3 次取锁失败 |

---

## 13. 并发锁

`change/.unattended.lock`（模块、PID、时间戳）：<30 分钟拒绝，≥30 分钟接管。
与 `change/.archive.lock` 是**两把不同的锁**。

---

## 14. 自动决策记录（强制审计）

写入 `04-review-report.md` 的「无人值守自动决策记录」表。**没有记录的自动决策 = 违规**。

---

## 15. 何时才该用自治模式

| 适合 | 不适合 |
|---|---|
| 需求已明确 | 需求还在探索 |
| 改动集中在 `GameCore` | 涉及资产/BP/关卡 |
| 有 L1 测试可验证 | 只能靠 PIE 肉眼看 |
| 单模块、低耦合 | 跨模块契约变更 |
