# 技术方案设计（brainstorm-develop）

> **HARD GATE**：在技术方案被用户批准之前，不要写任何实现代码。

## 定位

输入是**已明确的需求**。本阶段只回答"怎么做"，**不回头改需求**（要改需求就回 brainstorm-design）。

---

## 检查清单（按序完成）

1. **探索代码上下文** — 定位相关模块/类型、现有模块边界、依赖方向
2. **在途契约软检查** — 列出其它 wip 模块的在途契约
3. **逐轮澄清技术维度**（六个，一次一问）
4. **提出 2–3 个技术方案**（含分层落位、数据流、类型清单、性能、验证）
5. **分块展示** → 逐块确认
6. **写 `02-design.md`**（核心重点前置）
7. **产出 `07-spec-delta.md`**（涉及行为变更时）+ 在途契约终检
8. **调 plan-reviewer** → 写 `04-review-report.md` → 展示 → 确认
9. **衔接** — 提示 `/workflow plan`

---

## 阶段 1：探索代码上下文

必须深入到**类型与依赖**层面，不是读 README：

- 相关类型在哪个模块（`GameCore`/`GameFramework`/…）、属于哪一层
- 现有模块的公开接口（Gameplay 层暴露了什么 `UFUNCTION` / 委托）
- 数据从哪来（`UDataAsset` / `UDataTable` / 存档 / 运行时计算）
- 现有测试在哪（`Source/*/Private/Tests/` 或独立测试模块），如何构造测试替身
- **Blueprint 现状**：现有 BP 承担了哪些装配职责（划边界用）
- 已知技术债（`knowledge/{module}.md` 的「已知问题」章节）

**输出**：向用户展示"现有结构摘要"，确认没遗漏关键类型。

---

## 阶段 2：六个技术维度（一次一问）

| # | 维度 | 问题 | 选项示例 |
|---|---|---|---|
| 1 | **架构落位** | 新逻辑放哪？ | A 新增 `UGameInstanceSubsystem` B 扩展现有 Gameplay 类 C 纯 `GameCore` 规则 D 需改 `Build.cs` |
| 2 | **数据结构** | 状态存哪、怎么活？ | A `UDataAsset`/`UDataTable` B `USaveGame` C 运行时内存 D 混合 |
| 3 | **复制策略** | 客户端需要看到什么？ | A 不复制（仅服务器） B `Replicated` 属性 C Server RPC 回传 D 混合 |
| 4 | **性能** | 敏感点在哪？ | A Tick 频率 B 大量 Actor/Spawn C 加载卡顿 D 无明显瓶颈 |
| 5 | **兼容性** | 旧存档/旧资产怎么办？ | A 完全兼容 B `SchemaVersion` 迁移 C Core Redirect D 全新模块 |
| 6 | **验证** | 怎么证明做对了？ | A 纯 L1（无 World） B 需 L2（World/复制） C 需 L3/L4（人眼） D 需真机 |

> 维度 6 在 UE 版被提到必答位置：**方案必须连"怎么验证"一起设计**——尤其要说明核心逻辑能否脱离 `UWorld` 做 L1 测试，否则会产出"只能靠人眼看"的设计。

## 阶段 3：技术方案（2–3 个）

每个方案必须包含：

| 要素 | 内容 |
|---|---|
| 分层落位 | 新增/修改哪些类型，各在哪个模块，`*.Build.cs` 是否变动 |
| 数据流 | 配置 → Application → Domain → 持久化 → Presentation 的完整路径 |
| 关键类型清单 | 名称、层、职责、依赖 |
| 接口/事件契约 | 方法签名、事件名、参数（C1 契约） |
| 存档影响 | 是否改 schema、如何迁移（C2 契约） |
| 性能策略 | 对象池/缓存/避免每帧分配/预算 |
| 验证策略 | 哪些用例、什么级别（L0–L4） |
| 实现步骤 | 顺序 + 依赖 |
| 风险 | 技术风险与应对 |

给出**推荐方案 + 理由**（基于现有架构一致性、实现复杂度、验证成本）。

---

## 阶段 4：分块展示（4 节）

**第 1 节：架构总览**
- 落了哪几个模块、动了哪些 `*.Build.cs`
- 与现有模块的边界（谁调用谁、不调用谁）

**第 2 节：数据结构与契约**
- 类型定义（C++ 签名）
- 接口/事件表（名称 | 类型 | 方向 | 参数）
- 复制策略表（哪些状态复制、哪些仅服务器）
- 存档字段与 `SchemaVersion` 变化

**第 3 节：交互流程**
- 触发 → 校验 → 裁定 → 持久化 → 表现 的完整链路
- 生命周期（订阅/退订、初始化序、Ready 关卡）
- 错误处理与兜底

**第 4 节：性能与验证**
- 分配预算、对象池、缓存点
- 验证用例清单（含级别）

每节 ≤300 字；展示后问"这部分是否正确？"

## 阶段 5：写 `02-design.md`

**核心重点前置**：前半部分让人一眼看懂，后半部分补伪代码。

结构见 `模板/02-design.md`。必须包含：

```
★1 架构总览（新增什么、落哪层、一句话概括）
★2 关键类型清单（表）
★3 接入点（模块 / 注册 / 配置资产 / 存档）
★4 核心数据流
★5 实现步骤概要
--------
1 架构设计（模块定位、类型结构、依赖方向）
2 数据结构（类型定义、接口契约表、存档影响）
3 交互流程（时序、生命周期、错误处理）
4 性能与防御（分配预算、幂等、清理顺序、边界）
5 架构约束遵守声明（勾选清单）
6 风险评估（表）
```

### 架构约束遵守声明（必须逐条勾选）

- [ ] 类型放在正确模块，未引入反向依赖
- [ ] Gameplay 层是唯一写入口，Presentation 不直接改状态
- [ ] 权威模式与 `架构.md` 声明一致（Standalone / Dedicated）
- [ ] Server RPC 有 `HasAuthority()` 守卫与五项校验
- [ ] `UObject*` 成员都有 `UPROPERTY()` 且用 `TObjectPtr`
- [ ] 复制属性已在 `GetLifetimeReplicatedProps` 声明
- [ ] 外部输入已净化（NaN/越界/非法 ID）
- [ ] 委托绑定与解绑成对
- [ ] 存档变更有 `SchemaVersion` 迁移或 Core Redirect
- [ ] 业务逻辑未进 Blueprint（BP 只做装配）
- [ ] 等待有超时
- [ ] Tick 路径无查找/分配/同步加载
- [ ] 已写明验证策略（哪些用例、什么级别）

## 阶段 6：产出 `07-spec-delta.md` + 在途契约终检

**触发**：本次迭代涉及**可观察行为/契约变更**（新增能力、改数值阈值、改接口/事件签名、改存档字段）。
纯重构/纯性能优化/纯文档可免。

格式见 `模板/07-spec-delta.md`：
- `ADDED R{n}` — 新能力，编号必须是 spec 中不存在的新号
- `MODIFIED R{n}` — 改现存能力，整段替换
- `REMOVED R{n}` — 删现存能力
- 每条至少一个 `### 场景:`，含「当…」「则…」，**「则」必须落在权威端**

**在途契约终检**：逐项比对 `开发规范/工作流执行.md` 的 C1–C5：

| # | 契约 | 检查 |
|---|---|---|
| C1 | 接口/事件名 | 是否与在途模块同名冲突 |
| C2 | 存档字段 / `SchemaVersion` | 是否两个系统写同一存档字段 |
| C3 | 配置资产结构 | 是否同资产加字段导致对方读取崩 |
| C4 | 序列化引用/GUID | 是否重命名/移动资源导致引用失效 |
| C5 | 共享服务接口 | 是否改签名导致调用方断 |

- 有冲突 → 记 `05-issues.md`，按**阻断**处理，交 plan-reviewer 复核
- 0 冲突 → 在 `02-design.md` 头部记一行：
  `> 在途契约终检: 0 冲突（比对 N 个在途模块） 2026-11-12`

## 核心原则

- **代码先行探索** — 先读现有类型，再提方案
- **一次一问** — 技术决策必须逐个确认
- **架构一致性优先** — 不为单个功能引入新范式
- **权威边界清晰** — 状态变更只在 `Application`，表现层只发意图
- **验证内建** — 方案里写不清怎么验证，就不是完整方案
- **增量确认** — 分节展示，每节批准再继续
- **delta 是契约，不是愿望** — 写不出「当…则…」说明设计还没定
