# 需求头脑风暴（brainstorm-design）

> **HARD GATE**：在需求被用户逐块确认之前，不要产出设计文档、不要写代码。

## 与 brainstorm-develop 的分工

| | brainstorm-design（本技能） | brainstorm-develop |
|---|---|---|
| 输入 | 模糊想法 | 明确需求 |
| 关注 | **做什么？为什么做？给谁？** | 怎么做？架构？技术选型？ |
| 澄清维度 | 业务维度 | 技术维度 |
| 产出 | `01-requirements.md` | `02-design.md` |
| 典型错误 | 在这里讨论架构 | 在这里改需求 |

---

## 检查清单（按序完成）

1. **探索上下文** — 读相关代码、`knowledge/{module}.md`、`change/{module}/` 历史、近期 git log
2. **在途契约软检查** — 读 `change/versions.json`，列出其它 `status=wip` 模块在途的接口/数据/资产契约（只作输入，不阻断）
3. **逐轮澄清需求** — **一次只问一个问题**，优先给 3–4 个选项
4. **提出 2–3 个方向方案** — 精简 / 标准 / 旗舰，附取舍与推荐
5. **分块展示** — 每块确认后再进下一块
6. **写 `01-requirements.md`** → 最终审查
7. **调 plan-reviewer 审核** → 写 `04-review-report.md` → 展示 → 按答复整理
8. **衔接** — 提示下一步（`brainstorm-develop` 或 `/workflow plan`）

---

## 阶段 0.5：范围判断（先于澄清）

**问题**：这个主题能作为**一次** workflow 迭代吗？

| 判断 | 处理 |
|---|---|
| 涉及多个**可独立交付**的子系统（如"公会+跨服战+交易行"） | **提示拆分**，每次只聚焦一个 |
| 需要超过一次迭代的工期 | 建议先做最小闭环，其余排后续 |
| 范围合理 | 进入阶段 1 |

**标准**：如果做完后无法用一份 `01-requirements.md` 说清，就是太大。

---

## 阶段 2 的终止与追问规则

**结束条件（满足任一即停止提问）**：
1. 六大维度均已覆盖且回答明确
2. 用户主动说"够了/进入下一步"
3. 连续 2 个维度用户回答"不确定"（**跨维度全局停止**，剩余标【待定】）

**追问上限**：同一维度最多追问一次（"能具体说说吗？"）；仍不明确就标【待定】进入下一维度，不纠缠。

> 标【待定】不是失败——**假装确定才是**。待定项会在 Phase 1 的文档里显式列出。

---

## 阶段 5：产出后的规格自检（四项）

写完 `01-requirements.md` 后，以全新视角自查一遍，**发现问题直接内联修复**（无需重新审核）：

| # | 检查 | 判据 |
|---|---|---|
| 1 | **占位符扫描** | 有无"待定/TODO/未完成章节"？补齐，或明确标注"待 Phase 1 澄清" |
| 2 | **内部一致性** | 核心目标 ↔ 功能机制 ↔ 验收标准是否自洽？范围与不做什么是否冲突 |
| 3 | **范围检查** | 是否仍聚焦到一次迭代？变大则回头拆分 |
| 4 | **模糊性检查** | 有无一句话可被两种方式理解？若有，选一种明确写出 |

**自检记录**：在文档末尾加一行 `> 自检: 4/4 通过`（或列出未通过项）。

---

## 阶段 1：探索上下文

必须实际读，不得凭空假设：

- `Source/**` 中相关模块（`GameCore` / `GameFramework` / `GameServices` / `GameUI` / `GamePlay` 各在哪）
- `knowledge/{module}.md`（该模块已有的设计与坑）
- `change/{module}/` 下历史迭代（避免与已归档能力重复或冲突）
- 相关 `UDataAsset` / `UDataTable` 配置（数值从哪来）

**输出**：一段"现状摘要"给用户确认——"我理解现在的架构是…，这个需求要动的是…，对吗？"

---

## 阶段 2：逐轮澄清（六大业务维度）

**提问规则**：
- 一次一问
- 优先选择题（3–4 选项），允许自由输入
- 用户说"不确定"时：基于上下文给默认推荐，并标注 **【待定】**

| # | 维度 | 典型问题 | 选项示例 |
|---|---|---|---|
| 1 | 核心目标 | 这个功能解决什么问题？不做会怎样？ | A 提升留存 B 增加收入 C 修复体验断点 D 技术债 |
| 2 | 玩法机制 | 玩家如何触发、如何感知结果？ | A 主动点击 B 自动触发 C 条件解锁 D 组合 |
| 3 | 目标用户 | 谁会用到？新手/中期/硬核？ | A 新手 0–10 分钟 B 中期 C 硬核 D 全体 |
| 4 | 成功标准 | 怎么判断做成了？（可测） | A 完成率 B 使用频次 C 收入 D 崩溃/投诉下降 |
| 5 | 约束条件 | 时间/人力/平台/合规限制？ | A 一周内 B 需美术 C 需后端 D 纯客户端 |
| 6 | 引擎特有维度 | Standalone 还是 Dedicated？涉及存档改字段吗？要改 `UPROPERTY` 名吗？需要 BP 装配吗？ | A Standalone B Dedicated C 涉及存档迁移 D 涉及 UPROPERTY 改名 E 需 BP 装配 |

> 维度 6 是 UE 版新增：**只要需求涉及权威模式、存档结构、`UPROPERTY` 改名、Blueprint 装配，就会改变后续架构与验收标准**，必须在需求阶段问清。

---

## 阶段 3：方向方案（2–3 个）

每个方案写清：**做什么 / 不做 什么 / 代价 / 适用前提**。

```
方案 A（精简）：只做 X，不做 Y。1 人 3 天。风险：Z 场景体验缺失。
方案 B（标准）：做 X+Y。1 人 1 周。风险：需要新增配置表。
方案 C（旗舰）：X+Y+W。需美术+后端。风险：排期超两周。
推荐 B，因为 <基于上下文的理由>。
```

**禁止**只给一个方案——那等于替用户做了决定。

---

## 阶段 4：分块展示

按以下顺序，**每块单独确认**：

1. **背景与动机**（为什么现在做）
2. **核心目标 + 成功标准**（可测）
3. **玩法/功能机制**（触发、流程、结果、边界）
4. **目标用户与场景**
5. **约束与不做的事**（明确划出范围）
6. **验收标准表**（按 `开发规范/验证与门禁.md` §5 格式，含证据级别）

篇幅与复杂度匹配：简单功能几句话，复杂功能每块 ≤300 字。

---

## 阶段 5：写 `01-requirements.md`

用 `模板/01-requirements.md` 的结构。必须包含：

- 背景与动机
- 核心目标
- 功能机制（含边界与异常）
- 目标用户
- 成功标准（可测）
- 约束条件
- 引擎维度（单机/联机、存档影响、性能预算、平台）
- 方向方案与推荐
- **验收标准表**（含证据级别 L0–L4）
- 待确认问题

---

## 阶段 6：审核与衔接

1. 调 `plan-reviewer`（审核类型 `requirements`）
2. 结果写入 `change/{module}/_tmp/04-review-report.md`
3. `AskUserQuestion` 展示 → 确认 / 修复后重审 / 讨论
4. 通过后提示：

```
需求文档已生成: change/{module}/_tmp/01-requirements.md
下一步:
1. /brainstorm-develop   （做技术方案）
2. /workflow plan        （进正式规划，Phase 1 会跳过已确认的需求）
```

---

## 核心原则

- **想法先行，代码后置** — 本阶段不写任何实现代码
- **一次一问** — 不要一次抛 6 个问题
- **方案要有取舍** — 每个方案必须写"不做什 么"
- **验收必须可测** — 无法指定证据级别的验收标准等于没写
- **不确定就标【待定】** — 假装确定比承认不确定更危险
- **范围要显式** — "不做什么"和"做什么"同样重要
