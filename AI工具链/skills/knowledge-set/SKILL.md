# 知识沉淀（knowledge-set）

> **知识库记录"怎么做 / 为什么这么做 / 踩过什么坑"**，不记录"现在必须是什么行为"（那是 `spec/`）。
> 把契约写进知识库 = 制造第二真相源，禁止。

---

## 使用方式

```
/knowledge-set <module>
  changes:      <变更描述，可多行>
  source_files: <相关源文件，可选>
  dry_run:      true|false（默认 true）
```

---

## 步骤

1. **解析参数**：module、changes、source_files、dry_run
2. **定位文档**：`knowledge/{module}.md`
   - 不存在 → 新建（用 `knowledge/_TEMPLATE.md`）
   - 存在 → 增量更新（保留已有内容，不整篇重写）
3. **分析源文件**（若提供）：
   - 关键类型在哪个模块 / 哪一层
   - 公开接口与事件
   - 存档字段与配置依赖
   - 容易踩的边界
4. **判断该不该写进知识库**：

   | 内容类型 | 归属 |
   |---|---|
   | "系统必须做 X" | ❌ `spec/`（经 delta） |
   | "为什么选 A 不选 B" | ✅ knowledge |
   | "这个 API 有坑，必须…" | ✅ knowledge |
   | "改了哪些文件" | ❌ `change/03-plan.md` |
   | "性能预算 2ms" | ✅ knowledge（或本模块 spec 若属契约） |
   | "临时调试用" | ❌ 不要写 |

5. **dry-run**：展示将写入/修改的段落 diff 摘要，**不落盘**
6. **确认后写入**（`dry_run: false`），并更新文档头部「最后更新」
7. **更新索引**：`knowledge/README.md` 若新增模块，追加一行

---

## 知识文档结构

```markdown
# {Module} 模块知识

> 模块: {module}
> 关联层: Domain / Application / Presentation
> 关键类型: XxxService, XxxConfig
> 最后更新: YYYY-MM-DD

## 架构概述
<该模块在分层中的位置、核心职责、与谁交互>

## 关键类型
| 类型 | 层 | 职责 | 依赖 |
|---|---|---|---|

## 接口与事件
| 名称 | 类型 | 方向 | 参数 |
|---|---|---|---|

## 数据
<`USaveGame` 字段、`UDataAsset` 配置、运行时状态、复制情况>

## 使用约束
<调用顺序、幂等要求、性能红线、不可并发点>

## 踩过的坑
| 现象 | 根因 | 正确做法 |
|---|---|---|

## 已知问题 / 技术债
<待优化项，注明影响与暂缓原因>
```

---

## 什么算"值得沉淀的知识"

✅ 值得：
- 反直觉的行为（"这里必须先设 X 再设 Y"）
- 踩过一次的坑（现象 + 根因 + 正解）
- 设计取舍的理由（"没用 Addressables 因为…"）
- 不可见约束（"这个接口只能在主线程调"）

❌ 不值得：
- 代码里一眼能看到的事实（复述实现）
- 会过期的临时状态（"现在正在改 XX"）
- 与 `spec/` 重复的契约
- 没有根因的抱怨（"这块很难维护"）

> 判断标准：**一年后的人（或 AI）读到这条，能少踩一次坑吗？** 不能就别写。

---

## 注意事项

- **默认 dry-run**：先看 diff 再确认
- **增量不重写**：已有内容默认保留，只改需要改的段落
- **必须有"最后更新"日期**
- **不要写进 `spec/`**：那是归档时 delta 合并的专属区域
- **踩坑记录写"根因"而不只是"现象"**：只有现象无法预防复发
